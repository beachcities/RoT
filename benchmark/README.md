# ROT Benchmark（極小プロトタイプ）

同一のタスクを、**自己記述性の低いデータ**と**高いデータ**の両方で解かせ、成果あたりのトークン消費を比較するための最小構成です。

試論本体は [`../paper/return-of-token.md`](../paper/return-of-token.md) を参照してください。

## これは何を測るか

各試行について次を記録します。

| 記録項目 | 内容 |
| --- | --- |
| `repeat` | 何回目の反復か（1始まり）。反復ごとに会話は捨てて最初からやり直す |
| `status` | `ok` / `error`（通信が失敗して打ち切った試行） |
| `success` | 正答したか |
| `attempts` | 打ち切りまでに要求した回数 |
| `tokens_measured` | トークンを計測できたか。`usage` を返さないサーバでは `false` |
| `prompt_tokens` | 入力トークン（全試行の累計） |
| `reasoning_tokens` | 中間推論（CoT）トークン。取得できないモデルでは `null` |
| `output_tokens` | 最終出力トークン。CoT の内訳が取れないときは `null` |
| `completion_tokens` | 生成側の合計（CoT ＋ 出力）。内訳が取れなくても必ず入る |
| `total_tokens` | 全試行の累計（**失敗した試行を含む**） |
| `rot_per_1k` | `success / total_tokens × 1000`（1,000トークンあたり）。算出できないときは `null` |
| `attempt_log` | 試行ごとの応答・抽出した数値・トークン内訳 |

分母に失敗試行を含めるのは試論の中心的な主張によります。探索の大きさそのものが、データ側に欠けていた文脈の重さだという見方です。同じ理由から、通信が途中で失敗した場合も、そこまでに消費したトークンは捨てずに記録します（ただしその行は測定として不完全なので、集計からは除外します）。

`null` と `0` は区別します。`reasoning_tokens: null` は「内訳を取得できなかった」、`0` は「CoT を消費しなかった」です。同様に `rot_per_1k: null` は「算出できない」であって、`0.0`（＝解けなかった）ではありません。

### 採点規則

モデルの回答から数値を取り出す規則は次のとおりです。結果に効くので明示します。

1. NFKC で正規化する（全角数字を半角に落とす）
2. 桁区切り・空白・通貨記号を除去する
3. 残った整数の並びのうち**最後のもの**を答えとみなす

最初の数値を採ると「該当は1社です。売上は1200000000円です」の `1` を拾って誤答扱いになります。誤答扱いはリトライを誘発して分母を膨らませるため、測ろうとしている量そのものを歪めます。最後を採る規則にも「1200000000円（1200百万円）」のような後置注記を拾い損ねる弱点があるので、抽出結果は `attempt_log` の `extracted` に残してあり、あとから採点をやり直せます。

## これは何を測っていないか

- **分子は暫定的に正答/誤答の二値です。** 試論で挙げた三つの測り方（再生産コスト法・代替工数法・下流節約法）のいずれでもありません。成果の測定方法自体が未解決の課題です。
- **トークン数はトークナイザ依存です。** 異なるモデル間で `total_tokens` の絶対値を比較しても意味がありません。見るべきは**同一モデル内での、データ条件による比**です。集計もそのようにしか出しません。
- **自己記述的なデータは記述が増える分だけ入力が長くなります。** 総トークンの比を見るときは、入力側と生成側のどちらが動いたのかを分けて見る必要があります。集計はこの二つを分けて出します。
- **`reasoning_tokens` を返さないモデルがあります。** その場合は内訳が取れず、総量のみの比較になります。
- **試行数が極小です。** 現在タスクは3件、1セルあたりの反復は既定で5回です。比のばらつきを評価できる規模ではありません。反復回数それ自体の妥当性も未検討です（→「[反復回数について](#反復回数について)」）。
- **結果はまだ出ていません。** 自己記述性を高めればROTが改善する、というのは検証されるべき仮説であって、このリポジトリが示している事実ではありません。

## 実験設計

データ条件（raw / self-descriptive）× モデル（複数指定可）の総当たりで実行します。

試論では「軽量モデルほど自己記述性の効きが大きい」という交互作用を仮説として挙げています。これを見るには、能力の異なるモデルを少なくとも2つ指定してください。

### データとタスクの組（suite）

`suites/<名前>/` が1組です。`--suite` または `SUITE` で選びます。**組が違えば数値は比較できません**ので、どの組で走ったかは結果JSONと集計の見出しに残します。

データ条件は2つに限りません。`conditions.json` を置けば、そこに書かれた順で任意個の条件を読みます。各条件に何を置いたかも同じファイルに機械可読で書き、結果JSONの `condition_spec` にそのまま残します。`conditions.json` が無い組は `raw_dataset.json` / `self_descriptive_dataset.json` の2条件として読みます。`--conditions` で一部の条件だけに絞って走らせられます。

| 組 | raw 側に置いた手がかり | 実測の raw 正答率 |
| --- | --- | --- |
| `v1_unstated` | **なし**（単位が原理的に判定不能） | 0/5 |
| `v2a_emp` | 従業員数 | 1/6 |
| `v2b_emp_cap` | 従業員数 + 資本金（円建て） | 0/6 |
| `v2c_anchor` | 上記 + 外部の常識で桁が確かめられる実在企業1件 | 3/15 |
| `v2d_tax`（既定） | 上記 + 消費税額（円建て、`tax_24 / val_24 = 100000`） | 2/15 |
| `v3_levels` | 二値ではなく**10段階**に刻んだもの（下記） | 段による |

実測値は gpt-4o-mini・現行のプロンプトでのものです。組ごとの内訳と、なぜその手がかりを置いたかは各 `CLUES.md` に書いてあります。

### 自己記述性を段階に刻む（`v3_levels`）

高低の二値ではなく10段階に振った組です。**段は仮の刻みであって、検証すべき仮説ではありません。** 段の定義が正しいかを問うのではなく、消費が段に沿って動くかを見るための足場です。

二つの軸を混ぜてあります。**書き方の軸**（何も書かない → 項目名を意味のある語にする → 単位を明示する → コード・列挙値の意味を明示する）と、**参照の距離の軸**（同じレコード内 / 文書ヘッダ / 外部への参照だけを張り本体には書かない）です。直交しない組み合わせは作っていません。

| # | 水準 | 項目名 | 単位 | 業種コードの意味 | 活動状態 | 説明文 |
| --- | --- | --- | --- | --- | --- | --- |
| 0 | `l0_opaque` | 無意味 | なし | なし | `Y`/`N` | なし |
| 1 | `l1_names` | 意味のある語 | なし | なし | `Y`/`N` | なし |
| 2 | `l2_units_ref` | 意味のある語 | 外部参照のみ | なし | `Y`/`N` | なし |
| 3 | `l3_units_doc` | 意味のある語 | 文書ヘッダ | なし | `Y`/`N` | なし |
| 4 | `l4_units_record` | 意味のある語 | レコード内 | なし | `Y`/`N` | なし |
| 5 | `l5_codes_ref` | 意味のある語 | レコード内 | 外部参照のみ | `Y`/`N` | なし |
| 6 | `l6_codes_doc` | 意味のある語 | レコード内 | 文書ヘッダ | `Y`/`N` | なし |
| 7 | `l7_codes_record` | 意味のある語 | レコード内 | レコード内 | `Y`/`N` | なし |
| 8 | `l8_flags_record` | 意味のある語 | レコード内 | レコード内 | 真偽値＋廃業日 | なし |
| 9 | `l9_prose` | 意味のある語 | レコード内 | レコード内 | 真偽値＋廃業日 | あり |

**文書構造はどの段でも同じ**（`records` を持つオブジェクト）にしてあります。段の間で構造まで変えると、消費の差が構造の差なのか記述の差なのか分からなくなるためです。各段の内訳は [`suites/v3_levels/CLUES.md`](suites/v3_levels/CLUES.md) にあります。

タスクは**正答に何を要するか**で3群に分けてあります。混ぜたままでは、段のどこに境界があるかがタスクの難度に埋もれます。

| 群 | タスク | 正答に要る情報 |
| --- | --- | --- |
| `unit` | `task_01`〜`03` | 単位（百万円）。業種は社名から推せる |
| `code_guessable` / `flag` | `task_04`, `task_05` | 業種コードや活動状態の意味。ただしどちらも社名や廃業日の有無から推せる |
| `code_opaque` | `task_06` | `cd=303` の意味。社名（Zeta Holdings）からは推せず、書いてある段でしか解けない |

**境界は群ごとに別の場所に出ます。** `unit` 群は `l2`→`l3`（単位が文書に現れる箇所）、`code_opaque` 群は `l5`→`l6`（コードの意味が文書に現れる箇所）。`code_guessable` と `flag` の2群には境界が出ず、全10段で正答 5/5 のまま並びます。数値は `CLUES.md` にあります。

**タスクをまたいだ集計は、群の混合比で動きます。** 群の間で消費が2桁違うため、`水準ごとの消費` 表は参考にとどめ、タスク別の内訳表を見てください。

消費の主指標は**総トークン（CoT を含む）**です。試行回数も併記しますが、上限で頭を打つため連続量としては読めません。集計には上限に到達した件数を出します。

```bash
python plot_levels.py                       # results/ の最新
python plot_levels.py results/run_....json
```

水準を横軸、1試行あたりの総トークンを縦軸（対数）に置いた図を `results/` に PNG で保存します。中央値・四分位・個々の試行点に加えて、正答率と試行回数（上限線つき）を並べます。条件が3つ以上ある結果にだけ出します。

`--task <id>` でタスクを1つに絞れます。`--per-task` はタスクごとに1枚ずつ出します。**難度の違うタスクを混ぜた図は、水準ごとの中央値が混合比で動く**ので、境界を見るときはタスク別の図を見てください。

### 手がかりの設計方針

raw 側は「情報が欠けていて当てるしかない」条件ではなく、「推し量れば辿り着けるが、そのために試行と推論を要する」条件にします。

- **raw に単位や定義を書かないこと。** 書けば条件の差が消えます。
- **手がかりは必ず存在させること。** 他のレコードとの整合、桁の大きさ、別フィールドとの比、外部の常識など、推論で辿れる形で置きます。何を置いたかは `CLUES.md` に明示します。
- **難度を下げるためにタスクを易しくしないこと。** 測りたいのは欠けた文脈を埋める作業量であって、課題そのものの難しさではありません。
- 両条件は**同じ世界の同じレコード**を指していること。`suites/build_v2.py` が v2 系をひとつの定義から書き出しており、手がかりの有無だけが違います。

`v1_unstated` はこの方針を満たしていません（raw に単位の手がかりが無く、raw 側の消費が `MAX_ATTEMPTS × 再送長` で決まる定数になる）。比較のために残してあります。

### プロンプト

プロンプトは `prompts.json` に外出しし、`--prompt` / `PROMPT` で選びます。**投げた全文は結果JSONの `prompt_text` にそのまま残ります。**

いずれも、モデルに**考える過程を書くことを許し、最後の行の数値だけを採点対象にします**。「数値のみを出力せよ」と縛ると、欠けた文脈を埋める作業そのものを出力形式で封じることになり、ROT の分母が測るはずの探索が起きません（実測: その版では raw 側は正答0で、消費は打ち切り上限で決まる定数でした）。

リトライの文言は「各項目が何を表しているかという前提から見直して」の趣旨です。「データを読み直して」では同じ読みを繰り返すだけでした（実測: 3回とも同一の結論）。何をどう疑うべきかは言いません。

**raw と self_descriptive には必ず同一の文面を投げます。** 条件ごとにプロンプトを変えることはありません（`selftest.py` が、データ本体以外は一字一句同じであることを検査します）。

| キー | 中身 |
| --- | --- |
| `p1_baseline` | 現行版 |
| `p2_plain` | `p1` の言い換え。語順と語彙を変えたもの |
| `p3_terse` | `p1` の言い換え。常体にしたもの |

`p2` / `p3` は感度分析のための言い換えです。課題の変更や工夫の追加ではなく、特定の条件を有利にする表現も入れていません。リトライ文言も本文と対にして一緒に言い換えてあります（本文だけを変えて retry を固定する方法もありますが、疑いの対象は「言い回し全体に依存していないか」なので、対にして振っています。したがって本文とリトライの寄与は分離できていません）。

#### 言い回しへの依存を測った結果

文言を変えると結果が動くことが実測されている以上、条件間の差が言い回しに依存していないかは確かめておく必要があります。組 `v2d_tax`・`REPEATS=5`・gpt-4o-mini で、3種類のプロンプトをそれぞれ複数回実行した実測値です。

| プロンプト | ラン数 | raw 正答（/15） | ROT 比 | 総トークン比 | 総トークン中央値比 |
| --- | --- | --- | --- | --- | --- |
| `p1_baseline` | 3 | 6, 5, 4 | 5.51, 7.10, 10.52 | 0.454, 0.422, 0.356 | 0.346, 0.338, 0.331 |
| `p2_plain` | 2 | 4, 5 | 7.51, 7.04 | 0.499, 0.426 | 0.380, 0.397 |
| `p3_terse` | 2 | 8, 5 | 4.27, 7.93 | 0.439, 0.378 | 0.364, 0.330 |

- self_descriptive 側は7ランすべてで 15/15 でした。
- 比の向きは7ランすべてで同じでした（ROT 比 > 1、トークン比 < 1）。値は揃いません。
- **同一プロンプトを繰り返しただけの振れ幅が、プロンプト間の差を含んでいます。** `p1` を3回繰り返すだけで ROT 比は 5.51〜10.52 に振れ、この幅の中に `p2`（7.04〜7.51）も `p3`（4.27〜7.93）も入ります。raw 正答率も同様で、プロンプト内 4〜6（`p1`）・5〜8（`p3`）に対し、プロンプト間の差はその中に収まります。
- したがって、**この規模では3種類のプロンプトの間に差があるとは言えません**。言えるのは向きが揃ったことだけです。

二山の内訳では、self_descriptive 側は7ランすべて「解けず」が0件で、二山になるのは raw 側だけでした。raw の「解けた」試行の総トークン中央値は 696〜2432、「解けず」は 2812〜3617 です。

### 反復回数について

1セル（モデル × データ条件 × タスク）を既定で **5回** 繰り返します（`REPEATS` / `--repeats`）。反復のたびに会話を捨てて最初からやり直すので、各反復は独立した標本です。同じ会話の中でのリトライは `attempts` であって、反復とは別のものです。

繰り返すのは、条件間に差が出たときに、それが測定自体の揺れに収まるかどうかを言えるようにするためです。1セル1回では、差が出ても出なくても、揺れなのか条件の効果なのかを区別できません。

**5 という数字は暫定です。確定した設計ではありません。** 検出したい効果量や必要な検出力から導いたものではなく、「差の大きさが反復間のばらつきに対してどの程度かをまず見て、足りなければ増やす」という前提で置いた仮の値です。実際に走らせた結果を見て見直す対象です。

反復回数は実行時間とAPI呼び出し回数にそのまま比例します。既定では 1セルあたり最大で 5反復 × 3試行 = 15回の呼び出しになります。まず動かして確かめるだけなら `--repeats 1` から始めてください。

```bash
pip install -r requirements.txt

```

### APIキーを置く前に確認する

`--mock` を付けると、HTTPを一切叩かないダミー応答で全経路を通せます。APIキーは不要です。

```bash
python run_benchmark.py --mock          # 全シナリオを走らせて集計まで出す
python run_benchmark.py --mock --no-save
python selftest.py                      # 記録のされ方を検証する（外部依存なし）
```

`selftest.py` が確かめているのは「壊れていないこと」だけです。モックの応答はデータ条件を見ないので、この出力から仮説の当否は何も言えません。

用意してあるシナリオ（`mock_client.py`、モデル名で選ぶ）:

| モデル名 | 踏む経路 |

| `mock-no-usage` | `usage` を返さないサーバ（ROT を算出しない） |
| `mock-retry` | 2回外して3回目に正答（失敗分が分母に積まれる） |
| `mock-always-wrong` | 試行を使い切る |
| `mock-mixed-reasoning` | 試行ごとに内訳の有無が違う |
| `mock-empty` | 本文が空で返る |
| `mock-verbose` | 文章で返す（採点規則を踏む） |
| `mock-fullwidth` | 全角数字で返す |
| `mock-error` | 1回目から通信が落ちる |
| `mock-error-midway` | 途中で落ちる（そこまでのトークンは残る） |
| `mock-noisy` | 反復ごとに消費が揺れる（ばらつき表示の確認用の任意値） |
| `mock-flaky` | 反復のうち何回かだけ解ける（正答数 n/N の確認用） |
| `mock-varied` | データ条件で試行回数が変わる（集計表の書式確認用の任意値） |

### 集計

保存済みの結果に対して単体でも走ります。

```bash
python summarize.py                          # results/ の最新
python summarize.py results/run_....json
python summarize.py --json
```

モデルごとに、データ条件ごとの正答率・平均試行回数・トークン内訳・ROT を並べ、続けて `self_descriptive / raw` の比を出します。

- ROT は試行ごとの平均ではなく、条件ごとにプールして出します（`正答数 / その条件で投じた総トークン数 × 1000`）。試論の定義をそのまま条件単位に上げたものです。
- モデルを2つ以上指定した場合、モデル間で並べるのは**比だけ**です。総トークンの絶対値はトークナイザ依存で比較できないためです。
- `status=error` の試行と、トークンを計測できなかった試行は集計から除外し、除外した件数を明示します。

続けて、反復にわたるばらつきを出します。平均値だけでは分布の形が見えず、条件間に出た差がばらつきに対して大きいのかどうかを判断できないためです。

- 正答数 / 集計対象の反復数（例 `3/5`）
- 総トークンの中央値・四分位（Q1-Q3）・範囲（最小-最大）
- 反復ごとに算出した ROT の中央値と範囲

見出しの `ROT/1k` は従来どおり条件ごとのプール算出（`正答数 / 総トークン × 1000`）で、そこは変えていません。ばらつき表の `ROT/1k` はこれとは**別の量**です。反復1回ごとに算出した値で、解けなかった反復は 0 になるため分布は二山になり、その中央値はプール値と一致しません。両者は別物として読んでください。

条件間で総トークンの範囲が重なっているかどうかも注記に出します。**これは範囲を並べただけであって、検定ではありません。**

さらに、総トークンの分布を**解けた試行と解けなかった試行に分けて**併記します。解けた試行は打ち切りを待たずに終わり、解けなかった試行は上限まで使うため、分布は二山になります。混ぜたままの中央値は両者の混合比で動き、混合比は反復ごとに変わります。**分ける基準は `success`（正答したか）そのものです。**

### コマンドライン

| フラグ | 説明 |
| --- | --- |
| `--mock` | ダミー応答で全経路を通す（HTTPを叩かない） |
| `--models` | カンマ区切りのモデル名（`BENCHMARK_MODELS` を上書き） |
| `--max-attempts` | 1タスクあたりの最大試行回数を上書き |
| `--repeats` | 1セルあたりの反復回数を上書き（`REPEATS`） |
| `--suite` | データとタスクの組（`SUITE` を上書き。`suites/` 配下の名前） |
| `--prompt` | プロンプト一式（`PROMPT` を上書き。`prompts.json` のキー） |
| `--conditions` | 走らせるデータ条件をカンマ区切りで絞る（既定は組の全条件） |
| `--tasks` | 走らせるタスクIDをカンマ区切りで絞る（既定は全タスク） |
| `--show-trials` | 反復1回ごとの明細を表示する（既定は30件を超えると省略。JSONには常に入る） |
| `--no-save` | `results/` に書き出さない |

### 環境変数

`.env` はこのディレクトリに置いてください（リポジトリ直下から起動しても読みます）。

| 変数 | 既定値 | 説明 |
| --- | --- | --- |
| `API_KEY` | — | APIキー。ローカルサーバでは任意の文字列 |
| `BASE_URL` | `https://api.openai.com/v1` | OpenAI互換エンドポイント |
| `BENCHMARK_MODELS` | `gpt-4o-mini` | カンマ区切りのモデル名 |
| `MAX_ATTEMPTS` | `3` | 1タスクあたりの最大試行回数 |
| `REPEATS` | `5` | 1セルあたりの反復回数（暫定値。→「[反復回数について](#反復回数について)」） |
| `SUITE` | `v2d_tax` | データとタスクの組（`suites/` 配下の名前） |
| `PROMPT` | `p1_baseline` | プロンプト一式（`prompts.json` のキー） |
| `REQUEST_TIMEOUT` | `120` | 1リクエストのタイムアウト（秒） |
| `MAX_RETRIES` | `2` | 通信エラー時にSDKが再送する回数（測定上の試行回数とは別） |

`BASE_URL` を差し替えることで、vLLM や Ollama など OpenAI 互換 API を提供する任意のサーバに対して同じコードを実行できます。

```bash
# 例：ローカルの vLLM に向ける
BASE_URL=http://localhost:8000/v1 API_KEY=dummy BENCHMARK_MODELS=Qwen/Qwen3-4B-Instruct python run_benchmark.py
```

## 貢献を歓迎する箇所

- `suites/*/tasks.json` の拡充（現在はトイタスク3件のみ）
- raw 側の正答率をもっと安定させる手がかりの設計（現在は組によって 0〜40% と大きく振れる）
- 反復回数の設計（現在は既定5回。根拠は暫定で、見直しの対象）
- 分子の測定方法（二値からの脱却）
- 自己記述性の水準を連続量として扱う設計（現在は高/低の二値）
- 実データを用いたタスクセット
