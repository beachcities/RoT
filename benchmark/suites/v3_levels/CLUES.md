# v3_levels — 水準の記録

自己記述性を二値ではなく**10段階**に刻んだ組。`suites/build_levels.py` が生成する。

**段は仮の刻みであって、検証すべき仮説ではない。** 段の定義が正しいかを問うのではなく、
消費が段に沿って動くかを見るための足場として置いている。

## 二つの軸

* **書き方の軸**: 何も書かない → 項目名を意味のある語にする → 単位を明示する
  → コード・列挙値の意味を明示する
* **参照の距離の軸**: 同じレコード内に置く / 文書のヘッダに置く / 外部への参照だけを張って
  本体には書かない

直交しない組み合わせ（単位を書かずにコードの意味だけ書く、など）は作っていない。

## 段の一覧

各段に何を置いたかは `conditions.json` の `placed` に機械可読で入っており、結果JSONの
`condition_spec` にもそのまま残る。

## 設計上の取り決め

* **文書構造はどの段でも同じ**（`records` を持つオブジェクト）。段の間で構造まで変えると、
  消費の差が構造の差なのか記述の差なのか分からなくなる。
* 世界（5レコード）とタスク（3件）は `v2d_tax` と同一。単位を辿るための手がかり
  （`tax_24 / val_24 = 100000`）も全段に入っている。したがって `l0_opaque` は
  `v2d_tax` の raw とほぼ同じ内容だが、構造だけオブジェクトに揃えてある。
* 外部参照（`$schema`, `code_list_reference`）の URL は実在しない。本体に書かないことが
  何を意味するかを見るための段であって、参照先を取りに行けるかを見る段ではない。

## 段の切り方について分かったこと

**上位7段（`l3`〜`l9`）は分離していない。** 総トークン中央値は 850〜1022 に収まり、
正答率は全段 15/15、試行回数はすべて 1 回。単位が文書のどこかに書かれた時点で
（`l3`）タスクが1試行で解け、そこから先に何を足しても消費は動いていない。
**この課題では、段の解像度は `l0`〜`l3` にしかない。**

`l0` と `l1`（項目名を意味のある語にしただけ）も分離していない。中央値 17693 対 18270、
上限到達 6件 対 7件。

したがって、この10段は**上下に潰れている**。段を増やして解像度を上げるなら、`l2` と `l3`
の間（単位をどこに置くか）を細かく刻むか、上位段で差が出るだけの難度を持つタスクを
足す必要がある。段の切り方が課題の難度に対して粗すぎる、というのがこの組から言えること。

## 読むときの制約

**総トークンはほぼ試行回数の関数で、試行回数は10通りしか値を取らない。**
段差の比は「試行が何回で終わったか」の比とほぼ同じものを見ている。1.1倍という値は
「どちらも1試行で終わった」という意味で、そこに細かい差を読んではいけない。

`l2` の数値が反復間で安定しないことは以前の実測どおりで、モデル間比較でも同じ。
非単調な箇所（gpt-4.1-mini の task_06 で `l3` 10114 / `l4` 20168 / `l5` 8043、
gpt-5.4 の task_06 で `l4` 10261）は、この n では区別できない振れ。

# 逃げ道を塞いだ版（`org_007`〜`org_013` 追加後）

前版の `task_06` は「コードの意味が書いてある段でしか解けない」タスクとして設計したが、
6社のうち5社が社名から業種を推せたため、**消去法で「残った1社」に辿り着けた**。
実測で gpt-4.1-mini は `l1` から、gpt-5.4 は `l0` から、この経路で解いていた。

## 塞ぐために必要だった条件

1. **社名から推せない企業を複数にする。** 1社だけだと「残った1社」で確定する。
2. **それでも `cd` の値自体は見えている。** モデルはコード群を列挙して総当たりできる。
   単一業種を問うかぎり候補数 = 推せないコードの個数で、上限10試行なら候補が10以下で
   当たってしまう。単一業種のまま防ぐには推せないコードが11種類以上必要になり、
   レコードが増えすぎる。

したがって**推せないコードを6種類にし、問いを2業種の合計にした**。候補は
C(6,2) = **15通り**で上限10試行を超える。15通りの合計値は
`58, 91, 95, 117, 121, 130, 134, 152, 154, 156, 167, 189, 193, 215, 228` で、
**正答 228 は候補中で一意**（同じ値になる別の組み合わせがない）。

## タスクの逃げ道の分類

逃げ道を持つタスクは、**「手がかりがあれば書かれていなくても済む」ことを示す対照**として
意図的に残してある。分類は `tasks.json` の各タスクの `escape_route` に機械可読で入り、
結果JSONの `inputs` にもそのまま残る。

| タスク | 逃げ道 | 内容 |
| --- | --- | --- |
| `task_01`〜`03` | あり | 業種は社名から推せる（単位は推せない） |
| `task_04` | あり | 業種を社名から推せる。単位は不要 |
| `task_05` | あり | 活動状態は廃業日フィールドの有無から推せる |
| `task_06` | **なし** | 推せない業種が6コード。消去法不可、2業種合計で総当たりも尽くせない |

## 既知の副作用

* **追加した7社はすべて廃業にしてある。** そうすると `task_01`〜`task_05` の正答が前版と
  同一（1860000000 / 2750000000 / 850000000 / 80 / 430）のままになり、逃げ道の有無だけを
  変えた対照になる。**副作用として「社名から推せない ≒ 廃業」という相関ができている**
  （`org_006` Zeta Holdings のみ活動中）。`task_05`（活動状態）の解釈に影響し得る。
* **レコードが6件から13件に増え、プロンプトのデータ部分が約2.1倍になった**
  （`l0` 1301→2819字、`l9` 2518→5108字）。したがって**前版の数値と絶対量では比較できない**。
  比較できるのは段差の比だけ。

## 測定の範囲（案B）を選んだ理由

`task_04` と `task_06` の2タスクのみ、10水準 × 3モデルで測る。

* **逃げ道を塞いだ `task_06` と、逃げ道のある `task_04` が、同じラン・同じデータ量で
  並ぶ対照になる。** これが案Bを選んだ理由。
* `task_06` だけ（案C）では同一ラン内に対照が無い。データ量が2.1倍に変わっている以上、
  前版の `task_04` とはランをまたいだ比較になってしまう。
* 全6タスク（案A）は `task_01`〜`05` の再測定に費用の大半が消える。それらは正答も内容も
  前版と同一で測定済みなので、今回は見送る。

## 逃げ道は塞ぎきれていない（設計の欠陥）

`gpt-5.4` は `l0`〜`l5` で 14/30 正答している。応答を目視した結果、経路が特定できた。

> `industry_code` ですが、コードと業種名の対応表は明示されていません。…
> **この種の設問では通常、`industry_code` の 303 = 専門サービス業、404 = 学術研究業
> として集計します。**（`l1_names`）

> 該当する業種コードは明示されていませんが、**一般的な並びから**以下を対象と解釈します。
> 303 = 専門サービス業 / 404 = 学術研究業（`l2_units_ref`）

**消去法ではなく、コードの並び順による対応づけ**である。残っている手がかりは2つ。

1. **順序の一致。** 問いは「専門サービス業と学術研究業」の順で業種を挙げ、推せないコードは
   昇順に 303, 404, 505, 606, 707, 808 と並ぶ。**正答に必要な2つが先頭2つで、しかも同じ順**。
   「先頭2つを問いの順に割り当てる」だけで当たる。
2. **所属企業数の偏り。** 303 と 404 だけが2社ずつで、505/606/707/808 は1社ずつ。
   **2社ずつの群が2つしかない**ので、そこを選べば当たる。

候補を C(6,2)=15 通りと数えたとき、**コードの並び順と所属企業数という2つの識別子を
見落としていた**。実際の候補数はこれよりずっと少ない。

当たり方は安定していない（`l1` は前回のラン 5/5・今回 1/5、`l2` は前回 3/5・今回 5/5）。
当て推量の経路が使えるが確実ではない、という形になっている。

### 塞ぐための修正案（未実施）

* 問われる2業種を、**推せないコードの先頭2つ以外**に割り当て、かつ**問いで挙げる順と
  コードの昇順を一致させない**（例: 専門サービス業→606、学術研究業→303）。
* **所属企業数を揃える。** 推せないコードのうち少なくとも4つを2社ずつにし、
  「2社ずつの群」が識別子にならないようにする。企業を2〜3社追加する必要がある。

# 逃げ道を塞ぎ直した版（推せない企業12社・6コード各2社）

前版は「消去法を塞いだ」つもりで、**コードの並び順**と**所属企業数**という二つの識別子を
見落としていた。候補を C(6,2)=15 通りと数えたのは、6コードが互いに区別できない前提での
数え方で、実際には的が特定できていた。今回は**モデルが使える識別子を先に列挙**してから
設計した。

## 識別子の列挙

| # | 識別子 | 前版での状態 | 今回の対処 |
| --- | --- | --- | --- |
| I1 | **コードの昇順での位置** | 的が先頭2つ（303, 404）で、問いで挙げる順とも一致 | 的を 707（5番目）と 505（3番目）に置く。問いは専門サービス業→学術研究業の順で、コードは 707 > 505 の降順。位置も順序も一致しない |
| I2 | **コードごとの所属企業数** | 的の2コードだけが2社ずつ、他は1社ずつ | 推せないコード6つすべてを2社ずつにする（12社） |
| I3 | **レコードの出現順** | 的が推せない企業の先頭 | コード昇順に並べ、的は12社中の5・6・9・10番目。先頭でも末尾でもない |
| I4 | **社名の系列順** | ギリシャ文字順が I3 と相関 | I3 と同じ対処。的は Kappa/Lambda と Xi/Omicron |
| I5 | **群の規模（従業員数の合計）** | 未検討 | 群合計を 130/81/125/83/103/117 とし、的（125, 103）を6群中2位と4位にする。最大でも最小でもない |
| I6 | **活動状態との相関** | 推せない企業のうち1社だけ活動中だった | 推せない企業をすべて廃業にする。活動中は0社（副作用: `task_05` の正答が 430 → **375**） |
| I7 | 推せる／推せないの区別 | 101,201,202 が推せる側、3xx以上が推せない側 | **残す。** どれが的かは分からないので識別子にならない |

### 段差の大小は上限到達時の応答長でほぼ決まっている

| モデル | 上限10試行の平均 | 1試行の平均 | 比 | `l5`/`l6` 段差 |

44,556 / 64,001 / 27,712 という応答長の順である。細かい差を読むものではない。
