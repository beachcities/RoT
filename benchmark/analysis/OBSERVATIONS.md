## 見えたこと（観察。結論ではない）

### 1. 総トークンは、試行回数でほぼ決まっているように見える

[fig05](figures/fig05_attempts_vs_tokens.png) の左上と [counts.md の3節](tables/counts.md) が同じことを言っている。
試行回数を固定すると、総トークンの max/min は 1.1〜1.7倍に収まる。240試行すべてが水準もタスクも混ざったままでこれ。
一方、試行回数1回と10回の間では 733 → 41,482 と 50倍以上開く。

| 試行回数 | n | min | max | max/min |
|---|---|---|---|---|
| 1 | 151 | 733 | 1,137 | 1.55 |
| 3 | 14 | 2,693 | 3,855 | 1.43 |
| 5 | 5 | 7,704 | 8,655 | 1.12 |
| 7 | 5 | 12,261 | 18,270 | 1.49 |
| 10 | 28 | 23,998 | 41,482 | 1.73 |

[fig06](figures/fig06_within_trial.png) の左パネルでは、240本の累積曲線がほぼ1本の帯に重なる。
正答した試行（緑）も、上限まで回して正答しなかった試行（赤）も、同じ軌道の上を走っていて、
どこで止まったかだけが違う。

### 2. 水準が効いているのは「1試行あたりの消費」ではなく「何回試行するか」に見える

[counts.md の5節](tables/counts.md)：1試行目の入力トークンは (水準, タスク) ごとに完全に固定で、
l0 の 530〜539 から l9 の 833〜842 まで、水準の順に単調に増える。散らばりはゼロ（3runで完全一致）。
自己記述を足すほど入力は増えるが、その幅は 1.6倍でしかない。

対して試行回数の分布は水準で大きく違う（[counts.md の2節](tables/counts.md)）。

- l3〜l9: 試行回数はほぼ全部1回。222907Zの105試行中、2回に届いたのは4本、残り101本は1回で終わっている。総トークンは 739〜2,446。
- l0, l1, l2: 試行回数が上限まで広く散る。222907Zでは l0 が 2〜10回、l1 が 2〜10回、l2 が 2〜10回。
  1回で終わった試行は3run合わせて2本しかない（220208Z の l0/task_03、224435Z の l2/task_03）。

[fig02](figures/fig02_strip_by_attempts.png) では、l3〜l9 の行がほぼ全部濃紫（=1回）の1つの塊、
l0〜l2 の行だけが左から右へ色が連続的に変わる帯になっている。

### 3. l2_units_ref は、n=30 で見ると二山には見えない

[figures/hist/224435Z__l2_units_ref.png](figures/hist/224435Z__l2_units_ref.png) を4通りのビン幅で見ても、
はっきり分かれた2つの山は出てこない。742 の1点だけが孤立していて、その先は 1,837 から 34,112 まで
対数軸上でだいたい埋まっている。頻度軸を対数にしても、高い山の影に隠れた低い山は出てこない。

[figures/hist/222907Z__l2_units_ref.png](figures/hist/222907Z__l2_units_ref.png)（n=15）だと話が違って、
ビン幅 0.20 と 0.40 dex では二山に見える。5,522 と 12,261 の間が空いているためで、
その空白は試行回数 5回・6回・9回の試行がたまたま1本も出なかったことに対応している
（n=15 の試行回数の内訳は 2回:4, 3回:4, 4回:1, 7回:1, 8回:1, 10回:4）。
n=30 の run では 5回:2, 6回:2, 9回:2 が出ていて、その空白が埋まっている。

ビン幅 0.05 dex まで細かくすると、n=15 でも n=30 でも「二山」という形は消えて、
ばらばらの棒が並ぶだけになる。山の数はビン幅で変わる。

### 4. 中央値が動いた件は、分布の混合比というより「どの段に落ちたか」に見える

[counts.md の4節](tables/counts.md) に l2 の全点を昇順で並べてある。

- n=15（222907Z）: 中央値は8番目 = 3,855。その試行の試行回数は **3回**。
- n=30（224435Z）: 中央値は15・16番目 = 10,197 と 12,522。その試行の試行回数は **6回と7回**。

総トークンは試行回数に対して超線形に伸びる（会話を積むので入力側が二次的に伸びる、次節）。
だから中央の試行回数が 3 から 6〜7 にずれただけで、中央値は3倍動く。
中央値が実質的に報告しているのは「中央の試行回数」であって、そこには段差しかない。

### 5. 群と呼べそうな形が1つだけある。それは上限到達の山

[fig03](figures/fig03_strip_by_success.png) を見ると、赤い×（正答しなかった試行）は
l0・l1・l2 の右端だけに集まっている。数えると、正答しなかった27試行はすべて試行回数が上限の10回
（27/27）。逆向きは成り立たず、10回まで回して最後に正答した試行が1本ある
（224435Z / l2 / task_01 / 反復1 / 29,959トークン）。

つまり右端の塊は「難しい水準の分布の第2の山」というより、`max_attempts = 10` という壁に
押し付けられて溜まった点に見える。壁の位置を変えればこの塊の位置も変わるはずで、
これはデータの性質というより測り方の性質に見える。

### 6. タスクでも反復番号でも分かれて見えない

[fig04](figures/fig04_strip_by_task.png)。l0・l1・l2 の帯の中で3タスクは混ざっている。
l2（224435Z）では task_03 が最小値 742 と 20,203 の両方に出ているし、
task_01 は 6,397 から 34,112 まで散っている。
[表](tables/all_trials_by_tokens.md) を反復番号で追っても、若い反復が軽い・重いといった並びは見当たらない。

### 7. 「試行回数とは別の軸」の候補は見えるが、桁で言えば小さい

[fig05](figures/fig05_attempts_vs_tokens.png) の右下：1試行あたりの平均生成トークンは、
試行回数1回のとき 72〜481、10回のとき 305〜707 で、ゆるやかに増えている。
[fig06](figures/fig06_within_trial.png) の右パネルでも、試行を重ねるほど1回の返答が長くなる傾向が見える。

ただし総トークンの内訳は入力側が支配していて、最大の試行（41,482）では入力が 34,412、生成が 7,070。
生成の伸びは総量の動きの主役には見えない。

[fig07](figures/fig07_first_attempt.png) の右パネルでは、1試行目の生成量と、その試行が最終的に
何回かかったかの間に、目で追える関係が見えない。1回で終わった試行の1試行目は 72〜481、10回かかった試行の1試行目は 94〜530 で、
ほぼ同じ範囲に重なっている。

### 8. CoTの長さは、この結果からは見られない

`reasoning_tokens` は240試行すべてで 0。gpt-4o-mini がこのフィールドを返していない。
`output_tokens` は全件 `completion_tokens` と一致する。
依頼にあった「CoTの長さが効いているか」は、このデータでは判定材料がない。
代理として使えるのは生成トークンだけで、それは7節に書いた通り。

## 測定側で気づいた点（直していない。報告のみ）

1. **`reasoning_tokens` が全件0で、内訳としては機能していない。** 上の8節。
   `run_task` は「reasoning が None でないなら available」と扱うので、0 を返すモデルでは
   `output_tokens = completion - 0` になり、CoT列が常に0・output列が常にcompletionと同値になる。
   区別がつかないので、`reasoning_available` の判定を「Noneでない」ではなく
   「モデルがreasoning系か」で持つか、0固定の場合を別のフラグで残すと読み手が誤解しない。

2. **総トークンはリトライ手順に支配されている。** リトライは会話を捨てずに積むので、
   入力トークンが試行回数に対して二次的に伸びる（[fig06](figures/fig06_within_trial.png) 中央）。
   10回試行では総トークンの約83%が入力。「自己記述の量が消費を減らすか」を総トークンで測ると、
   測っているものの大半はリトライ回数×会話長になる。
   1試行目だけの消費、あるいは「正答までの試行回数」自体を主指標にすると、この混入がなくなる。

3. **`max_attempts = 10` が吸収壁として効いている。** 上の5節。分布の右端の塊は上限の位置で決まる。
   上限を変えた再実行がないと、この塊が「解けない試行の消費量」なのか「上限の位置」なのか、
   結果からは切り分けられない。

4. **`attempts == 10` は「失敗」と同義ではない。** 10回目で正答した試行が1本ある。
   要約でこの2つを同一視すると、成功率と消費の対応がずれる。

5. **`rot_per_1k` は総トークンの逆数に成功/失敗を掛けたものなので、上の1〜3をそのまま受け継ぐ。**
   試行回数が1増えるだけで値がおよそ半分になるため、この指標の中央値も同じ理由で不安定になる。

6. **結果JSONに入力データの指紋が入っていない。** `condition_spec` にはファイル名と `placed` があるが、
   データ本体もハッシュもない。今回3runを並べてよいかは、(水準, タスク) ごとの1試行目の入力トークンが
   3runで完全一致することから確認した（l2/task_01 なら3run全部 637）が、これは
   「たまたま一致を見られた」だけで、保証ではない。実際いま作業ツリーの `suites/v3_levels/*.json` は
   別セッションが編集中で、6件目のレコードが足されている。次のrunの結果は入力が変わった状態のもので、
   結果ファイルだけを見て区別する手段が今はない。suiteのハッシュを結果に書き足すと後で困らない。

7. **n=15 と n=30 は入れ子の標本ではなく、別々のrunである。** 222907Z（反復5）と 224435Z（反復10）で、
   前者は10水準、後者は2水準を回している。中央値の3倍の差には、標本数の差だけでなく
   run間の差も混ざっている。同じrunの中で前半15本と全30本を比べたわけではない。

## 見えなかったこと・やっていないこと

- **群の数は決めていない。** 混合分布の当てはめもクラスタリングもしていない。
  「二山」と言えるかは、上の3節の通り、ビン幅とnで見え方が変わる。
- **統計的検定はしていない。** 差の有無についての判定は一切していない。
- l3〜l9 の内部では、総トークンの分布に分かれた群は見えない。1回で終わる点が 739〜1,137 に集まり、
  そこから離れた点は 222907Z で4本、224435Z で3本あるだけで、すべて試行回数2回のもの。
- l0・l1・l2 の帯の中に、試行回数以外で分かれる境目は見つけられなかった。
  タスクでも反復番号でも1試行目の長さでも分かれない。
- 上の観察は gpt-4o-mini・prompt_set = p1_baseline・max_attempts = 10 の3runに対するもの。
  他のモデルや他の上限で同じ形になるかは、このデータからは分からない。
