## 0. この案が採った線引き

「解釈」と「開示」の境目を、次のように引いた。

| 書く | 書かない |
| --- | --- |
| 何を測ったか（条件・手続き・記録項目） | その数字が仮説について何を示すか |
| **なぜその測り方を選んだか**（設計判断とその理由） | なぜその数字になったか（因果の帰属） |
| 数値そのもの（条件を添えて） | 数値から導かれる主張 |
| この測り方では何が言えないか（留保） | この測り方で何が示せたか |

**設計判断の理由は残す。** リファレンス実装に求められるのは「何をどう決めたか」の開示なので、
「分母に失敗試行を含めるのは、探索の大きさ自体を欠けた文脈の重さと見る立場によります」のような
記述はむしろ核であって、削る対象ではない。削るのは、**出た数字に理由をつける文**である。

現行READMEはこの線をおおむね守っている。抵触するのは後述の3箇所だけである。

## 4. この案が触っていない箇所と、その理由

| 箇所 | 触らない理由 |
| --- | --- |
| 「これは何を測るか」の記録項目表 | 何を記録するかの開示そのもの。解釈は入っていない |
| 分母に失敗試行を含める理由の段落 | 設計判断の理由。リファレンス実装の核であって、削る対象ではない |
| 「採点規則」節 | 手続きの開示。規則の弱点まで自分で書いてある |
| 「これは何を測っていないか」の他の項目 | 留保の列挙。この案の線引きでは「書く」側 |
| 「言い回しへの依存を測った結果」節 | 数値と、そこから何が**言えないか**の記述。「差があるとは言えない」は留保であって、仮説の裏づけではない |
| 「反復回数について」節 | 5回が暫定であることを自分で書いている。開示 |
| 「実験設計」「手がかりの設計方針」 | いずれも設計判断とその理由 |
| 「貢献を歓迎する箇所」 | 未解決の課題の列挙。開示 |
| モックのシナリオ表・コマンドライン・環境変数 | 手続きの開示 |

現行READMEは、留保と設計理由をよく書いている。**リファレンス実装としての改訂で足りないのは、
位置づけの明示と、事実として古くなった3〜4箇所の修正である。** 全面的な書き直しは要らない。
