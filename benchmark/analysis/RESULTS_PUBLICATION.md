# 実測結果を公開すべきか、するならどの形か

`results/` は現在 `.gitignore` に入っている（`.gitignore` の1行目「実行結果（生成物。実測値は
リポジトリに含めない）」）。リファレンス実装として公開するにあたり、この方針を続けるかどうか。

**判断は依頼者が行う。** ここでは選択肢と、それぞれの利点・難点を並べる。

---

## 0. いま `results/` にあるもの

| 区分 | ファイル数 | 容量 |
| --- | --- | --- |
| 実測の結果JSON | 22 | 4.45 MB |
| モック実行の結果JSON | 6 | 0.64 MB |
| 図（PNG） | 9 | 1.14 MB |
| 合計 | 37 | 6.23 MB |

いちばん大きい1本（`run_20260819T235549Z.json`, `v3_levels` 10水準 × 6タスク × 5反復 = 300試行）の内訳:

| 何を残すか | 容量 | 全体に占める割合 |
| --- | --- | --- |
| 全部 | 1.98 MB | 100% |
| 応答本文（`answer` / `final_answer`）を落とす | 0.45 MB | 23% |
| `attempt_log` ごと落とす | 0.19 MB | 10% |
| `summary` だけ | 0.06 MB | 3% |

**容量の77%は応答本文である。** そして応答本文は、再採点・抽出規則の検証・モデルが何を
推論したかの確認にとって、いちばん要るものでもある。落とすと軽くなるが、
落としたものがそのまま検証できないものになる。

`d28768b` 以降の run には `inputs`（タスクと各条件のデータ本文）が入る。
`v3_levels` で数十KB程度なので、上の見積りをほとんど動かさない。

## 1. 公開の前に踏まえておくこと

### 1.1 いまある22本の実測は、入力を同定できない

`d28768b` より前の世代なので、`inputs` を保存していない。
`backfill_fingerprints.py` が後付けした印にも `unrecoverable` として明記されている。

これが実害になる例が現にある。`v3_levels` の run 4本のうち3本は5レコード版、
1本は6レコード版で走っており、結果ファイルからその違いは読めない
（詳細は [REFERENCE_READINESS.md](REFERENCE_READINESS.md) 2.1）。

**入力を同定できない結果を公開すると、再現できない数値が出典つきで引用されうる。**
公開するなら、この点を明記するか、対象から外すかのどちらかが要る。

### 1.2 モック実行を混ぜてはいけない

6本はモック応答である。`mock: true` が入っているので機械的には見分けられるが、
同じディレクトリに並べると誤読される。少なくとも置き場所を分ける。

### 1.3 探索の途中の run をどう扱うか

22本のうち、`v1_unstated` から `v2a`〜`v2d`、プロンプトの言い換え比較まで、
設計を詰める過程の run が大半を占める。

- 出す利点: 「なぜその設計にしたか」の証拠になる。README が挙げている実測値
  （組ごとの raw 正答率、プロンプト間の振れ幅）の出どころが辿れる
- 出す難点: どれが参照点なのかが分からなくなる。数が増えるほど、
  引用する側が古い run を掴む危険が上がる

### 1.4 権利と個人情報

- **個人情報は無い。** データは合成で、企業名も架空。公開の障害にならない
- **APIキーの混入も無い。** `base_url` は残るが鍵は残らない。全ファイルを確認した
  （1本に `api_key` の語があるが、`dummy` を拒否された401エラーの本文であって鍵ではない）
- **応答本文はモデルの生成物である。** リポジトリの `benchmark/` 以下は Apache 2.0 で
  提供すると `LICENSE-NOTICE.md` に書いてあるが、**モデルの出力を自分のライセンスで
  再配布してよいかは自明ではない**。実務上は問題にならないと考えられるが、
  リファレンス実装として出す以上、`LICENSE-NOTICE.md` に一文を足すのが筋
  （「`results/` に含まれるモデルの応答本文は、生成に用いたAPIの利用条件に従う」など）

### 1.5 gitに置くことの性質

結果ファイルは追記ではなく毎回新しいファイルとして増える。1本2MBなので、
run を重ねると履歴が積み上がる（gitは過去の版も保持する）。
**参照点として固定する少数の run に絞る**か、リポジトリ外（リリース添付、Zenodo等）に置くか。

## 2. 選択肢

### 案A: 公開しない（現状維持）

- 利点: 判断が要らない。容量も権利も考えなくてよい
- 難点: **リファレンス実装として成立しない。** 「こういう条件で測ったらこうなった」の
  「こうなった」が無い。READMEに書かれている実測値（組ごとの正答率、プロンプト間の振れ幅、
  水準ごとの境界）の出どころが読者に辿れない。第三者は追試しかできず、再計算も照合もできない

### 案B: 実測の生JSONを全部出す（22本、4.45 MB）

- 利点: 探索の過程がすべて開示される。設計判断の証拠が揃う。
  READMEの数値がどの run のものか、読者が突き合わせられる
- 難点: 22本のうち21本は入力を同定できない世代のもの（1.1）。
  参照点がどれか分からない（1.3）。容量が大きい

### 案C: 代表となる1ランだけ出す（1.98 MB）

- 利点: 参照点が1つに定まる。「この条件で測ったらこうなった」がそのまま指せる。
  応答本文まで揃うので、再採点も抽出規則の検証もできる
- 難点: 反復や条件を変えた run と比べられない。
  READMEに書かれている他の数値（プロンプト間の振れ幅など）の出どころが辿れないまま残る。
  代表に選んだ run が `d28768b` 以前なら、入力を同定できない状態で公開することになる

### 案D: 全ランから応答本文を落として出す（22本で約1 MB）

- 利点: 軽い。数値の再計算はできる。試行ごとのトークン内訳・正誤・試行回数は残る
- 難点: **再採点ができない。** 抽出規則の弱点（READMEが自ら挙げている
  「1200000000円（1200百万円）」型の後置注記）を第三者が検証できない。
  応答本文はこの測定でいちばん検証価値の高い部分である

### 案E: 要約だけ出す（`summary`、22本で約0.3 MB）

- 利点: いちばん軽い。READMEの数値の裏づけにはなる
- 難点: 検証できるのは「集計コードが正しく動いたか」だけになる。
  分布の形も個々の実行も見えない。前回の分析で分かったのは、**この測定では要約統計量が
  分布の形を代表しない**ということなので、要約だけを出すのは、いちばん誤読されやすい形を
  いちばん見えやすい場所に置くことになる

### 案F（併用）: 参照点の1ランを全文、それ以外は数値のみ

- 構成:
  - `results/reference/run_….json` — 参照点となる1ラン（応答本文込み、`inputs` 込み）
  - `results/reference/trials.csv` — 公開する全ランの試行ごとの数値（応答本文なし）
  - `results/reference/RUNS.md` — 各 run が何のための実行か、前と何が違うかの台帳
  - それ以外の作業 run は引き続き `.gitignore`
- 利点: 参照点が定まり、かつ検証にいちばん要る部分（応答本文）が揃う。
  容量は2〜3 MBに収まる。作業 run で履歴が膨らまない
- 難点: 何を参照点にするかを決める必要がある。
  台帳は自動生成できないので、人が書いて維持する必要がある

## 4. 補足（決めるときに要るであろうこと）

- **どの案でも、`d28768b` 以降で走らせ直した run を公開の対象にするのが筋である。**
  既存22本は、公開するとしても「入力を同定できない、設計の過程の記録」という位置づけになる。
  現在の `suites/` は6レコード・6タスクに変わっているので、いま走らせ直せば
  `inputs` 込みの run が得られる
- 公開するなら `.gitignore` の書き換えが要る。`benchmark/results/` を除外したまま
  `!benchmark/results/reference/` を足す形が素直
- 図（PNG）はコミットしなくてよい。`plot_levels.py` と `analysis/figures.py` が
  結果ファイルから再生成できる。ただし `results/` が除外されていると、
  読者は図を再生成できない（結果を公開すればこの問題も消える）
- `LICENSE-NOTICE.md` にモデル応答の扱いを一文足す（1.4）
- **私の見立てとしては案F。** 参照点が定まることと、検証にいちばん要る応答本文が残ることを
  同時に満たすのがこの形だけである。ただしこれは判断材料であって、判断ではない

## 5. 決まったこと（2026-08-23）

判断は依頼者による。ここは記録。

### 5.1 案F を採る

参照点となる1ランを応答本文込みで公開し、それ以外のランは数値のみ、台帳を添える。
作業中のランは引き続き `.gitignore`。実装は測定側が `results/reference/`
（参照ラン3本・`RUNS.md`・`trials.csv`）として済ませている。

### 5.2 旧3ランの応答本文は現在の版から落とす。履歴は書き換えない

[tables/all_trials_by_tokens.md](tables/all_trials_by_tokens.md) と `.csv` には、
220208Z / 222907Z / 224435Z の240試行について応答の冒頭60字が入っていた。
この3本は参照点として扱わないと決めたランなので、本文を載せたままにすると 5.1 の方針と食い違う。
そこで**列ごと落とした**（数値・水準・タスク・反復・試行回数・正誤は残している）。

**履歴からは消さない。** 理由は次のとおり。

- 落とした本文は**合成データに対するモデルの応答**であり、個人情報でも認証情報でもない
  （実在企業を含むのは `v2c_anchor` / `v2d_tax` のデータで、この表には入っていない）
- 現在の版から落とすのは**公開方針に揃えるため**であって、流出への対処ではない。
  急いで消さなければならない性質のものではない
- 公開済みの履歴を書き換えると、既存の clone やフォーク、コミットSHAを指した参照が壊れる。
  **そのリスクのほうが大きい**

したがって、`db33f7e` 以前のコミットからは応答本文つきの表が読める状態が続く。
表そのものにもこの旨を注記してある。
