## 0. 「検証できる」には三通りある

要るものが違うので分けて考える。

| | 何をするか | 必要なもの |
| --- | --- | --- |
| **A. 追試** | 自分のAPIキーで同じ手続きを走らせ直す | コード、投入データ、プロンプト、実行条件、モデルの指定 |
| **B. 再計算** | 公開された結果ファイルから、採点・集計・図をやり直す | 結果ファイル、採点規則、正解、集計コード |
| **C. 照合** | 当時の実行が本当にその通りだったかを確かめる | 実行時のコードの版、投入データの指紋、応答のメタ情報 |

`d28768b` 以降に走らせる run では、A と B が成立する。C は部分的に成立する
（コードと入力の同定はできるが、応答側のメタ情報が無い）。

いま `results/` にある28本は `d28768b` より前の世代で、**入力の本文を保存していない**。
したがってこの28本については B が成立せず、C も成立しない。この区別は公開の判断に直結する
（→ [RESULTS_PUBLICATION.md](RESULTS_PUBLICATION.md)）。

## 2. 欠けているもの

### 2.0 いま解決したこと（記録として）

`d28768b` で入ったもの:

- `inputs` に**タスクの本文と各条件のデータ本文そのもの**が入るようになった
- `fingerprint` に入力・プロンプト・コードの内容ハッシュ、gitのコミットと `dirty` が入るようになった
- `backfill_fingerprints.py` が既存の結果に後付けの印を押した。復元できないものを
  `unrecoverable` に理由つきで明記し、**現在の `suites/` をハッシュして古い run に当てはめることはしていない**

最後の一点は妥当な判断である。当てはめれば、結果ファイルが支えられないことを主張することになる。

この判断の結果として、既存28本は「入力を同定できない結果」として残る。
その28本を分類する間に合わせは、この `analysis/` の側にある
（→ [tables/input_fingerprint.md](tables/input_fingerprint.md)、2.1）。

### 2.1 既存28本の入力は復元できない — 公開の判断に直結する

これは仮定の話ではない。`results/` にある `v3_levels` の run 4本は、2種類の入力に分かれている。

| run | 走った時刻(ローカル) | 条件数 | タスク | 入力 |
| --- | --- | --- | --- | --- |
| 220208Z | 07:02 | 10 | 3件 | 5レコード版 |
| 222907Z | 07:29 | 10 | 3件 | 5レコード版 |
| 224435Z | 07:44 | 2 | 3件 | 5レコード版 |
| 235549Z | 08:55 | 10 | 6件 | **6レコード版**（`org_006` Zeta Holdings が追加されている） |

結果ファイルの中に、この違いを直接示す記録は無い。`suite` はどれも `v3_levels`、
`prompt_set` はどれも `p1_baseline`、`condition_spec` も同一である。

気づけたのは間接的な方法による。同じ条件・同じタスクの**1試行目の入力トークン数**を比べると値が動く。

| 条件 / タスク | 220208Z | 222907Z | 224435Z | 235549Z |
| --- | --- | --- | --- | --- |
| `l2_units_ref` / `task_01` | 637 | 637 | 637 | **728** |
| `l9_prose` / `task_03` | 833 | 833 | — | **944** |

全件は [tables/input_fingerprint.md](tables/input_fingerprint.md)（`input_fingerprint.py` が生成）にある。
28本を「入力が両立するまとまり」に分けると14群になる。同じ条件名 `raw` / `task_01` でも
入力トークンは run によって 231〜537 に分かれている。名前は同じである。

**これは本物の指紋の代わりにはならない。長さが変わらない改変は検出できない。**
数値の書き換え、同じ長さの語への置換、正解だけの修正——どれもこの方法では見えない。
`backfill_fingerprints.py` が `unrecoverable` と書いているのは正しい。

さらに、走った時刻とそれを記述したコミットの順序が逆である。

| run | 走った時刻 | それを記述したコミット | コミット時刻 |
| --- | --- | --- | --- |
| 222907Z | 07:29 | `a4f17c1` 10段階に刻む | 07:30 |
| 224435Z | 07:44 | `9b83c8c` 境界の再実行 | 07:45 |
| 235549Z | 08:55 | `de0f7fa` タスクを群に分ける | 08:57 |

いずれも走らせてからコミットしている。既存28本には `git.dirty` の記録が無いので、
走った時点のコードとデータが直後のコミットと同一だという保証は無い。

公開の前提に関わる。**入力を同定できない結果を公開すると、再現できない数値が出典つきで引用されうる。**

### 2.2 応答したモデルの実体が分からない

`gpt-4o-mini` は日付つきスナップショットへの別名である。APIの応答は実体名
（`gpt-4o-mini-2024-07-18` のような）と `system_fingerprint` を返すが、
コードは `choices[0].message.content` と `usage` しか読んでおらず、どちらも捨てている。

別名の指す先はプロバイダの都合で変わる。半年後に同じ名前で走らせても、
同じモデルに当たったかを言う手段が無い。入力側の指紋が揃った今、
**同定できていないのはモデル側だけになっている。**

### 2.3 サンプリング設定が指定も記録もされていない

`client.chat.completions.create(model=model, messages=messages)` で、temperature も top_p も
seed も max_tokens も渡していない。したがってプロバイダの既定値で走っている。
その既定値が何だったかは結果に残らない。

反復（`repeats`）は「会話を捨てて独立な標本を取る」ためのもので、その揺れの出所が
まさにこのサンプリングである。出所の設定が記録されていない。

seed を指定していないので、同じ入力でも同じ出力にはならない。それ自体は
「揺れを見たい」という設計として筋が通るが、**そう決めたことがどこにも書かれていない。**
決めたことが書かれていないのは、リファレンス実装としては欠落にあたる。

### 2.4 `finish_reason` が記録されていない

`max_tokens` を指定していないので上限で切れることは稀だが、切れた場合、
採点規則が「最後の数値を採る」ため、途中で切れた応答は誤答として記録される。
誤答はリトライを誘発し、分母を膨らませる。つまり `finish_reason: "length"` は
測ろうとしている量を直接歪めるが、後から検出する手段が無い。

応答のIDと生成時刻も記録されていないので、プロバイダ側のログとの照合もできない。

### 2.5 実行環境が記録されていない

- 実行したコマンドライン。`--conditions` や `--tasks` で絞ったかどうかは、
  結果の一覧と組の定義を突き合わせないと分からない
- openai SDK の版、Python の版、OS
- 実行の開始・終了時刻（`run_at` は保存時刻。個々の試行の時刻は残らない）
- `MAX_RETRIES` は `fingerprint.settings` に入るようになったが、これは**SDKが通信エラー時に
  暗黙に再送する回数**で、実際のAPI呼び出し回数は `attempts` と一致しない。
  そう読めるようREADMEに一文があるとよい

### 2.6 READMEに載っている数値のうち、いま `results/` に辿れないものがある

`benchmark/README.md` 61〜69行目の「実測の raw 正答率」表を、`results/` にある実測run と
突き合わせた結果。

| 組 | READMEの記載 | `results/` にある実測run から数えた値 |

| `v1_unstated` | 0/5 | **該当する run が1本も無い** |

保存後に消した run、あるいは組の別の世代の値だと思われるが、**その由来を確かめる手段が無い。**

同じ突き合わせを「言い回しへの依存を測った結果」の表（153行目付近）でやると、

## 3. 提案：残りに何を記録すれば足りるか

実装は測定側の担当。ここでは記録する項目と形だけを挙げる。
入力側は `d28768b` で埋まったので、残るのは**応答側と実行環境**である。

### 3.1 各試行の各回（`attempt_log[]`）に足す

```json
{
  "attempt": 1,
  "answer": "…",
  "finish_reason": "stop",
  "response_model": "gpt-4o-mini-2024-07-18",
  "system_fingerprint": "fp_0f03d4f0ee",
  "response_id": "chatcmpl-…",
  "started_at": "2026-08-19T23:55:51Z",
  "latency_sec": 2.31
}
```

`response_model` と `system_fingerprint` は試行ごとに変わりうる（プロバイダ側の切り替え）ので、
run 単位ではなく attempt 単位で持つのが安全。実測で常に同じなら、集計側で1つにまとめて表示すればよい。
既存の `null` / `0` の扱いと同じく、**返ってこなかった場合は `null`** にして、
「返らなかった」と「空だった」を区別する。

### 3.2 `fingerprint` に `request` と `runtime` を足す

```json
"request": {
  "temperature": null,
  "top_p": null,
  "seed": null,
  "max_tokens": null,
  "note": "null は未指定。プロバイダの既定値で走っている"
},
"runtime": {
  "argv": ["run_benchmark.py", "--suite", "v3_levels", "--repeats", "5"],
  "python": "3.13.1",
  "openai_sdk": "1.51.0",
  "platform": "Windows-11-10.0.26200",
  "started_at": "2026-08-19T23:55:49Z",
  "finished_at": "2026-08-20T00:56:02Z"
}
```

`request` は**現状を変えずに記録するだけ**の案である。`temperature=0` のように明示指定するのは
測定の変更にあたるので、そこは測定側の判断。**変えないという判断も、書いてあれば開示になる。**

### 3.3 優先順位

| 優先 | 記録するもの | これが無いとできないこと | 手間 |
| --- | --- | --- | --- |
| 1 | `response_model` / `system_fingerprint` | モデルの同一性の主張。入力側が揃った今、ここだけが穴 | 小 |
| 1 | `request`（未指定であることを含めて明示） | 揺れの出所の開示 | 小 |
| 2 | `finish_reason` | 切れた応答の検出（いまは誤答と区別がつかない） | 小 |
| 3 | `runtime`（argv / SDK版 / Python版 / 開始終了時刻） | 環境差の切り分け | 小 |
| 4 | `attempt_log[].response_id` / `started_at` | プロバイダ側ログとの照合、時間帯の影響の確認 | 小 |
| 5 | `git.dirty` が真のときの汚れたファイル一覧 | どこが未コミットだったかの特定 | 小 |

### 3.4 記録以外に足せるもの

- **`--verify` モード。** 保存済みの結果ファイルを読み、`fingerprint` を現在の `suites/` /
  `prompts.json` / コードに突き合わせて一致・不一致を出す。
  「この結果は今のコードで再現できる／できない」が一目で分かる。
  ハッシュを入れた意味は、突き合わせる道具があってはじめて現れる。
- **`results/RUNS.md` の台帳。** run ごとに、何のために走らせたか・何が前回と違うかを1行で。
  ハッシュがあれば差分は機械的に出せるが、**なぜ変えたか**は人が書くしかない。
- **保存前の警告。** `git.dirty` が真なら「作業ツリーが汚れた状態で走らせた」と標準出力に出す。
  公開の対象にする run は、汚れていない状態で走らせるのが望ましい。
- **`CLUES.md` の自動生成部分。** レコード件数やタスク件数は `build_levels.py` が知っているので、
  手書きの記述（2.6）が古びない形にできる。
